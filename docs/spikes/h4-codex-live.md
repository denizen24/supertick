# H4: адаптер Codex — живые проверки (13.11.2026)

Codex CLI 0.167.2, вход по ChatGPT. Плагин ставится `tools/install-codex.sh` (локальный маркетплейс →
`codex plugin marketplace add` → `codex plugin add supertick@supertick-local`), набор попадает в
`~/.codex/plugins/cache/supertick-local/supertick/<версия>/`. Codex показывает модели путь к SKILL.md
навыка плагина: от него навык считает корень набора, если не задан `$SUPERTICK_ROOT`.

## Песочница ведущего

Ведущий запускает исполнителей из своего shell (`codex exec`, `cursor-agent`, `kimi`), и они наследуют его песочницу.

| Песочница ведущего | Дочерний `codex exec --sandbox read-only` |
|---|---|
| `workspace-write` | не стартует: `failed to initialize in-process app-server client: Read-only file system` (пишет в `~/.codex`) |
| `workspace-write` + `network_access=true` + `--add-dir ~/.codex` | стартует и отвечает, но ни одной команды не выполняет: `error building bubblewrap command: app-server socket directory must be a user-owned directory with mode 0700` (песочница в песочнице) |
| `danger-full-access` | работает: `ls` выполнен, запись `child.txt` отклонена (`Read-only file system`) — песочница исполнителя держит |

Решение: ведущий Codex — `codex --sandbox danger-full-access` (`launch` в профиле печатает именно так).
Роль ограничивает песочница её исполнителя: роли чтения — `read-only`, кодер — `workspace-write` с записью
в каталоги `.git`. Поэтому на Codex неназначенная роль идёт движком `codex` с моделью ведущего, а не
родным субагентом: у `spawn_agent` нет своей песочницы, он наследует полный доступ ведущего.

В спайке S0-CX этого не было видно: исполнители там были локальными моками без сети и без записи в `~/.codex`.

## Проба ведущего: `gpt-5.6-sol` — `passed`

`SUPERTICK_LIVE=1 python3 -m unittest test_codex_host.LiveCodex` (из `tools/tests`), 985 с, с первого раза.
Все девять проверок зелёные: 18 запусков через `run-engine.sh`, 16 ожиданий `supervisor-wait.sh --mode shared --max 1500`
на переднем плане, после CHANGES REQUESTED продолжен тот же кодер, три задачи DONE с ревью и приёмкой, финальный
тик без P0/P1, коммиты только мок-кодера, `.git` не тронут. Замечания `tests` нет: в отличие от k3, ведущий
не запускал тесты сам. Сторож `.git` ведущий вызвал оба раза (`lead:git-guard`, `lead:git-check`, «Git Guard: OK»).

## Приёмка H4: SIMPLE из установленного плагина, настоящие исполнители

Песочница с `src/textutil.py`, задача «char_count и тесты», `--complexity=simple --force-team --coders=1`.
Профиль: ведущий `codex gpt-5.6-sol`, роли без назначения; поверх — корневые роли владельца из
`~/.claude/agent-teams.json`. Получилось: кодер, рецензент, приёмщик — `codex gpt-5.6-sol`; сверка задач,
спецификация и наследие — `cursor` (смешанные движки под ведущим Codex). Около 35 минут, один ход
(`codex exec … --json`, 118 команд shell).

- три задачи DONE: у каждой ревью APPROVED, приёмка PASS и коммит кодера (`54cc2b7`, `ac53c06`, `8b76c63`);
  кодер коммитил сам из `workspace-write` с записью в `.git`;
- ведущий ждал внутри хода и ход не заканчивал до сводки;
- `.git/hooks` — только образцы, `.git/config` не изменён: `git-guard.py check` даёт `GIT GUARD OK` и у
  ведущего, и при независимой сверке;
- сверка задач PASS, спецификация PASS, наследие CLEAN; дерево вне `.supertick/` чистое.

Найдено и починено:
- **Двойные отчёты.** Исполнители с правом записи (кодер Codex, cursor в режиме записи) сами писали файл
  `REPORT:`, а `run-engine.sh` клал ответ движка рядом как `-001`. У cursor таким ответом оказалась
  вступительная реплика («Выполняю перекрёстную проверку…»). Теперь, если файла отчёта до вызова не было, а
  исполнитель создал его сам, отчётом считается этот файл (`report_by=engine_file`), копии нет.

Кандидаты для V1 (промахи модели, не адаптера):
- `## Tests` фазы 3 ведущий отдал роли `acceptance-checker` (только чтение), а не `ci-verifier`. `py_compile`
  упал на записи `.pyc`, отчёт `VERIFY TESTS: BROKEN`, итог `ENVIRONMENT_BROKEN` при зелёных тестах.
  В LEAD.md это сказано, но одной фразой в длинном пункте: вынести роль проверяющих в таблицу.
- Задачу «тесты» план поставил после задачи «код», а критерий задачи 1 требовал `python3 -m unittest`: кодер
  честно эскалировал (0 тестов, код 5). Правило «критерий задачи — только её собственные проверки» в шаблоне
  плана стоит подчеркнуть.
- Ответ cursor `composer-2.5` бывает вступительной репликой вместо отчёта (два отчёта `-malformed1`; ведущий
  продолжил исполнителей, как велит протокол). Это поведение движка, к Codex не относится.

## Итог

Приёмка H4 выполнена: живой SIMPLE из Codex дошёл до DONE, ведущий ждал внутри хода
(`supervisor-wait.sh`), кодер коммитил с записываемым `.git`, `.git/hooks` и `.git/config` сверены после
прогона. Отдельный git-worktree для кодера (мера R11 в ТЗ) не делали: сторож закрывает тот же риск
обнаружением, а worktree добавил бы протоколу шаг слияния. Если владелец захочет, это отдельная задача.
