# Продолжение проверки SuperTick

Карточка движка и его процесс используют один `timeoutSec`. Укажи его до запуска.
`run-engine.sh --status RUN NAME` показывает срок и источник, а `.done` содержит фактическое завершение.
Вызов `run-state.py take RUN RUN/engine/NAME/NNN.out` возвращает JSON. При сбое поле `report` может быть
пустым, а `artifact` указывает на сохранённый вывод. Даже код 124, полученный от самого CLI, отличается
от остановки по сроку. Лимит провайдера блокирует повтор на том же движке; после подтверждения сброса
разреши его явно через `engine-config.py argv … --retry-quota`.

## Изолированные проверки

Передай свой JSON-план, в котором команды задаются массивами аргументов. Это доверенная конфигурация
проекта. Копирование файлов и чистое окружение не заменяют песочницу ОС. Запускай команды в исполнителе,
ограниченном тестовым окружением. Записывать разрешается в scratch внутри RUN. В `env` перечисляй только
тестовые значения. Для Mongo/Redis/SQL используй отдельную локальную тестовую службу, без боевых данных.

```json
{
  "env_templates": ["backend/.env.example"],
  "env": {"MONGO_URL": "mongodb://127.0.0.1:27029", "CI": "true"},
  "test_db_prefix": "one_to_one_pytest_",
  "git_context": true,
  "steps": [
    {"id": "backend", "cwd": "backend", "argv": ["/path/to/test-venv/bin/python", "-m", "pytest", "-q"]},
    {"id": "frontend", "cwd": "frontend", "argv": ["yarn", "build"]}
  ]
}
```

```bash
python3 scripts/run-checks.py run --repo REPO --run-dir RUN --id ci --executor verify-ci --plan plan.json
python3 scripts/run-checks.py run --repo REPO --run-dir RUN --id ci --executor verify-ci --plan plan.json --resume
python3 scripts/run-checks.py bind --repo REPO --run-dir RUN --id ci --commit HEAD
```

Укажи `--lock /path/to/resource.lock`, если проверки делят ресурс. Для независимых окружений общей
блокировки нет. Ожидание показывается в `state/checks` вместе с владельцем ресурса. Его предел задаёт
`--queue-timeout`; время ожидания отдельно от срока выполнения и тестов. Передавай имя карточки в
`--executor`, чтобы supervisor мог связать запрос с настоящим исполнителем.

Можно добавить `"copy_dependencies": {"frontend/node_modules": "/path/to/private/node_modules"}`.
Зависимости копируются физически, их содержимое участвует в отпечатке. Внешние ссылки и посторонние
`.env*` отклоняются до тестов. Пропускаются только перечисленные отслеживаемые обычные `.env.example`.
Используются отдельные HOME и TMPDIR, а также уникальный DB_NAME. `SUPERTICK_TRACKED_MANIFEST` даёт список
скопированных файлов и хеши. При `git_context: true` скрипт `$SUPERTICK_GIT_TRACKED <paths...>` выдаёт
список из Git-коммита без изменения глобального окружения Git.

По умолчанию вход шага включает все проверенные файлы. Для проекта с чёткими границами можно задать
`inputs` как список шаблонов путей. Перечисли все зависимости шага и конфигурацию, иначе старый PASS может
стать неприменим. При смене проекта или тестового окружения выбери новый id. `--only id` выполняет выбранные
устаревшие или упавшие шаги и сохраняет остальные с действующим отпечатком. Устаревший пропущенный шаг имеет
OUTDATED, итог остаётся неполным. После остановки прежние логи в каталогах попыток сохраняются, RUNNING
перепроверяется. Команда bind сравнивает файл в Git, включая бит исполнения, со снимком.

## Права исполнителей и ручная приёмка

На одноразовом связанном Git worktree создай обычный пустой файл `supertick-probe-canary` в корне, в
`git rev-parse --absolute-git-dir` и в `git rev-parse --git-common-dir`. Под фактическим исполнителем
запусти `probe-access.py --repo REPO --access read|write`. Для проверяющего с тестами дополнительно укажи
`--scratch RUN/tmp --test-port PORT`. Проба не меняет канарейки и проверяет доступ к локальному порту.
Наличие доступа к порту не подтверждает работоспособность приложения; для этого нужен свой тестовый шаг.

Если хост может запускать нативного исполнителя, `engine-config.py argv … --native-available` при известном
конфликте Codex CLI со связанным worktree предлагает нативный запуск с причиной. У хоста без этой возможности
проверь режим CLI на пробном дереве и при проблеме используй обычный отдельный клон. Не снимай песочницу.
При смене исполнителя зафиксируй назначение и причину в DECISIONS.md.

После явной ручной приёмки пользователем запиши коммит, причину и ссылку на подтверждение.

```bash
python3 scripts/run-state.py manual-accept RUN 4 commit=SHA 'reason=…' 'evidence=…'
```

Затем поставь DONE в PLAN.md. Исторические отчёты FAIL сохраняются. Для документов используй отдельную
проверку фактов и относящийся к ним `git diff --check`, если это команда текущего Tooling.


`supervisor-tick.py status RUN` выводит фазу, время последнего события, оставшиеся задачи и проверки,
число фактических вызовов по ролям и отдельно число заведённых карточек нативных исполнителей.
Подтверждай запуск нативного исполнителя через `run-state.py set … status=running` после того, как хост
его запустил. Observe выводит замечания о превышении бюджета, без остановки.
